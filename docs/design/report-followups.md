## 1. 확인 결과

### 6. Windows 경로 정규화 — 버그 1건, 수정함

- **확인 범위:** 경로를 문자열로 비교하는 곳 전체(`git grep`). 대부분 `Path.resolve()` 값끼리 비교하거나, 같은 함수가 만든 문자열끼리 비교한다.
- **버그:** `agent_dev/adapters/worktrees.py` `WorktreeManager.validate()`가 Git의 `--git-common-dir` 출력 문자열과 저장된 `common_dir`(`str(Path.resolve())`)을 그대로 비교했다. Windows에서 Git은 `C:/x/.git`, Python은 `C:\x\.git`으로 쓰므로 항상 다르다.
- **영향:** `validate()`를 쓰는 변경 검토(`development_review.py`)와 게시(`publishing.py`)가 Windows에서 "다른 저장소의 워크트리"로 막힌다. 작업 취소 시 워크트리 정리도 건너뛴다.
- **수정:** 두 값을 `Path(...).resolve()`로 바꿔 비교한다. 테스트 `test_validate_compares_git_paths_not_their_spelling`는 수정 전 실패, 수정 후 통과.
- 저장소 경로 바인딩(`project_setup.py` 440행)은 양쪽 모두 `git_root()`의 `resolve()` 결과라 문제없다.

### 11. 비정상 종료 후 복구 — 빈틈 있음

- **현재 동작:**
  - 강제 종료 후 다시 실행하면 `recover_attempts()`가 실행 중이던 시도를 `interrupted`로 표시한다.
  - 역할 실행 전 `role_before()`가 워크트리 파일 목록과 해시를 **메모리에만** 기록하고, 실행 후 `enforce()`가 역할 정책(읽기 전용 여부, 쓰기 범위)과 대조한다.
- **빈틈:** 단계가 도중에 죽으면 `enforce()`가 실행되지 않는다. 다음 실행은 그 상태를 새 기준선으로 잡는다. 그래서:
  - 읽기 전용 역할(검토자 등)이 죽기 전에 쓴 파일이 검사 없이 남는다.
  - 개발 역할의 반쯤 쓴 변경이 다음 시도에 섞인다(이건 의도로 볼 수도 있다).
  - 모듈 범위 밖 변경은 게시 단계의 `validate_publish_paths`가 다시 막는다. 따라서 위험은 **모듈 범위 안에서 역할 정책을 어긴 변경**에 한정된다.
- **설계:**
  1. 시도를 시작할 때 `before` 캡처를 작업 산출물 폴더에 `attempts/<attempt_id>/before.json`으로 저장한다(파일 경로와 해시만, 내용 없음).
  2. (구현: 기준선은 `<작업 폴더>/.attempts/<attempt_id>.json`에 파일 해시와 Git 트리 객체로 저장한다. 앞 단계들의 변경은 게시 전까지 커밋되지 않으므로 HEAD가 아니라 이 트리로 되돌린다. 이어서 실행하는 것이 "되돌리기" 선택이다.)
  3. `recover_attempts()`로 `interrupted`가 된 시도가 있으면, 같은 노드를 다시 실행하기 전에 현재 워크트리를 그 `before`와 비교한다.
     - **변경 없음:** 그대로 진행한다.
     - **변경이 그 역할 정책 안:** `InterruptedChangesKept` 이벤트를 남기고 진행한다(개발 역할의 반쯤 쓴 작업은 이어 쓴다).
     - **정책 위반:** 변경을 패치 파일(`attempts/<id>/interrupted.patch`)로 보관하고, 작업을 `INTERRUPTED_CHANGES` 사유로 차단한다. 사용자는 작업실에서 "버리고 이어서 실행" 또는 "차단 유지"를 고른다. 버릴 때는 `git checkout -- <path>`와 새로 생긴 파일 삭제로 해당 경로만 되돌린다.
- **바꿀 곳:** `application/workflow.py`, `workflow_dag.py`(시도 시작·재개), `adapters/phase_catalog.py`(캡처 저장·비교), `task_queries.py`·`execution_view.py`(사유 문구), 작업실 행동 1개.
- **테스트:** 읽기 전용 노드가 파일을 쓰고 죽는 상황을 만든다(러너가 파일을 쓴 뒤 예외를 던지고, 시도 행을 `running`으로 남김). 재실행 시 차단되는지, 개발 노드의 정책 안 변경은 이어지는지 확인한다.

### 13. 외부 작업 중복 — PR은 안전, Slack은 재전송 가능

- **PR (안전):** 게시는 `publish:<task>:<repo>:<snapshot digest>` 요청 키와 `publish_records`로 한 번만 처리된다. 푸시 뒤 죽으면 `gh pr list --head <branch>`로 기존 PR을 먼저 찾는다. PR이 두 개 만들어지는 경로는 없다.
- **로컬 완료 (안전):** 커밋 후 `publish_records`를 쓰기 전에 죽어도, 재실행 때 `publish_repository`가 "커밋할 변경 없음"으로 건너뛰고 현재 HEAD를 기록한다. 고칠 것이 없다.
- **Slack (빈틈):** `poll_once()`가 메시지를 처리하고 답장을 보낸 뒤, 폴링이 끝날 때 한 번만 상태(`processed`, `cursor`, `task_states`)를 저장한다. 중간에 `slack.post`가 실패하면 앞서 처리한 메시지의 답장과 상태 변경 알림이 다음 폴링에서 다시 나간다. 명령 자체는 `slack-<channel>-<ts>` 요청 ID로 한 번만 실행된다.
- **설계:**
  - 메시지마다 `processed`와 `cursor`를 먼저 저장하고 답장을 보낸다(답장은 최대 한 번).
  - 답장 전송이 실패하면 `recent`에 실패를 기록하고 화면의 "최근 처리"에 보인다.
  - 알림은 작업별로 보낸 직후 `task_states[task_id]`를 갱신·저장한다.
- **바꿀 곳:** `adapters/messenger.py`(`poll_once`, `_follow`, `_notify`).
- **구현:** 메시지 답장, 백그라운드 결과 답장, 상태 알림 모두 보내기 직전에 상태를 저장한다. 전송이 실패한 그 한 건은 다시 보내지 않고(최대 한 번) 리스너 오류로 남는다.
- **테스트:** 가짜 Slack 클라이언트가 두 번째 `post`에서 예외를 던지게 하고, 다음 폴링에서 첫 답장이 다시 나가지 않는지 확인한다.

### 22. 러너 샌드박스 차이 — 보고서와 반대

| 러너 | 코드 역할이 쓸 수 있는 도구 | 셸 실행 | 네트워크 |
|---|---|---|---|
| Codex | 샌드박스 `workspace-write`(읽기 전용 역할은 `read-only`) | 가능(샌드박스 안) | 없음(Codex 기본) |
| Claude | `Read,Grep,Glob,Edit,Write`(`--tools`) | 불가 | 없음 |
| Gemini | 읽기 도구 + `write_file`, `replace`(관리자 정책) | 불가 | 없음 |

- **실제 차이:** Codex 개발 역할은 테스트를 직접 돌려 보며 고칠 수 있고, Claude·Gemini는 코드만 쓰고 DevRoster 검증 단계에서야 결과를 본다. 그래서 검증 실패 후 재진입이 Claude·Gemini에서 더 잦을 수 있다.
- **설계 — 승인된 검증 명령 도구:** DevRoster가 MCP 도구 `run_project_check(gate)` 하나를 제공한다.
  - 프로필의 승인된 검증 명령만, 해당 워크트리에서, 기존 `run_gate` 경로(출력 상한, 시간 제한, 비밀값 가림)로 실행한다.
  - 임의 셸이 아니므로 권한이 늘지 않는다. Claude는 `--mcp-config`로, Gemini는 정책에 이 도구만 허용해 붙인다. Codex에는 붙이지 않는다(이미 셸이 있음).
  - 호출 횟수와 시간은 작업 실행 한도에 포함한다.
- **결정 필요:** 기본으로 켤지(권장: 개발 역할만 켬), 호출당 시간 제한(권장: 검증 명령 자체의 제한을 그대로 사용).
- **바꿀 곳:** `adapters/tool_gateway.py`(도구 정의), `cli_runner.py`(역할별 연결), `runners/gemini_cli.py`(허용 목록), 문서.
- **규모:** M.

## 2. 큰 기능

### 17. 빠른 수정(Fast-track)

- **현재:** 개발 흐름 프리셋 `quick-fix`(developer, qa, reviewer)가 있다. 하지만 작업을 만들려면 작업실에서 `design.refine` → `design.approve` → `plan.create` → `plan.approve` → `task.run`을 따로 실행하거나, Studio에서 기획서 → 명세 → 목업 → 인계를 거쳐야 한다.
- **목표:** "무엇을 고칠지" 한 문단과 대상 모듈만 입력하고, **확인 대화상자 한 번**으로 실행까지 간다. 승인 기록은 그대로 남긴다.
- **설계:**
  1. 작업실에 `quick.start` 행동을 추가한다. 입력은 제목, 설명(최대 4,000자), 모듈, 완료 기준(선택, 없으면 "설명한 문제가 재현되지 않는다").
  2. 서버가 미리보기를 만든다. 설계 문서(설명 + 완료 기준 + 범위 = 모듈의 수정 허용 경로), 작업 1개짜리 계획, 흐름 `quick-fix`, 예상 실행 한도.
  3. 확인 대화상자에 미리보기를 보여 준다. 사용자가 확인하면 한 요청 안에서 설계 저장과 승인, 계획 생성과 승인, 스냅샷, 실행 시작을 처리한다. 승인 주체는 그 사용자이고, 이벤트에 `fast_track: true`를 남긴다.
  4. 제한: 모듈 1개, 흐름 `quick-fix` 고정, 데이터베이스나 권한 관련 경로(설정의 보호 경로)를 건드리면 일반 절차로 안내한다.
- **바꿀 곳:** `adapters/agent_console.py`(행동, 미리보기 다이제스트), `state/sqlite/store.py`(한 트랜잭션 안에서 설계·계획 생성), 작업실 화면, Slack 명령(`빠른수정 <모듈> <설명>`, 선택).
- **테스트:** 확인 한 번으로 승인 2건과 작업 1건이 생기는지, 미리보기 후 입력이 바뀌면 거부되는지(`STALE_VERSION`), 보호 경로가 거부되는지.
- **결정 필요:** Slack에서도 허용할지(권장: 1차는 화면만).

### 23. 명세서 2단계 생성

- **현재:** `studio_generation.prompt_for("specs")` 한 번의 호출로 요구사항, 화면, 질문, 22종 문서를 모두 만든다. 응답 상한은 65,000자다. 긴 기획서에서 문서가 얕아지거나 JSON이 잘리면 전체가 실패한다.
- **설계:**
  1. **1단계, 요구사항:** `requirements`, `screens`, `questions`만 만든다. 짧고 빠르며, `validate_specs`의 요구사항·화면 규칙과 인용 검사를 그대로 쓴다. 질문이 있으면 여기서 멈추고 답을 받는다(지금의 질문 흐름 유지).
  2. **2단계, 문서 묶음:** 22종을 4묶음으로 나눠 묶음마다 한 번씩 호출한다. 입력은 확정된 1단계 결과와 기획서다.
     - 기획·요구: 개발기획서(원문 보존, AI 호출 없음), 요구사항명세서, 기능명세서, 정책정의서, 비기능요구사항정의서, 용어사전
     - 화면·데이터: 화면정의서, API명세서, 데이터정의서, 테이블정의서, 권한정의서, 공통코드정의서
     - 설계: 기술설계서, 프로세스정의서, 시스템다이어그램, 시퀀스다이어그램, 클래스다이어그램, 프로그램목록
     - 검증·관리: 테스트시나리오, 요구사항추적성매트릭스, 갭분석및보완사항, 산출물목록
  3. 묶음 하나가 실패하면 그 묶음만 한 번 다시 시도한다. 그래도 실패하면 작업을 "일부 문서 실패"로 끝내고, 그 묶음만 다시 생성할 수 있게 한다(25번과 같은 경로).
  4. 진행 표시: 기존 Studio 진행 표시(작업 heartbeat)에 "요구사항 → 문서 1/4 … 4/4"를 보인다.
  5. 저장: 모든 묶음이 끝나면 한 개의 명세 리비전으로 저장한다. 중간 결과는 작업 폴더에만 둔다.
- **바꿀 곳:** `adapters/studio_generation.py`(단계 실행, 묶음 프롬프트), `domain/studio.py`(묶음 검증 함수), `studio.js`(진행 표시), Studio 사용 설명서.
- **비용과 시간:** 호출 수는 1회에서 5회로 늘지만, 각 응답이 짧아 실패 재시도 비용이 줄어든다. 묶음 2~4는 서로 독립이라 병렬 실행도 가능하다(1차는 순차, 동시 실행 한도 고려).
- **테스트:** 가짜 생성기로 묶음 하나가 실패할 때 그 묶음만 재시도되는지, 최종 리비전이 22종을 모두 가지는지, 1단계에서 질문이 나오면 2단계를 실행하지 않는지.

### 25. 문서별 재생성

- **현재:** 문서 하나만 바꾸려 해도 명세 전체를 다시 생성한다.
- **설계:** 명세 화면의 문서마다 "이 문서 다시 생성"(선택: 고칠 점 입력)을 둔다.
  - 생성 작업 종류 `spec_documents`: 대상 문서 이름 목록, 현재 리비전, 사용자 메모를 입력으로 받는다. 다른 문서는 제목과 요약(앞부분 일부)만 맥락으로 준다.
  - 결과는 현재 리비전을 복사해 대상 문서만 바꾼 **새 리비전**으로 저장한다. `validate_specs` 전체 검사를 다시 통과해야 한다.
  - 요구사항이나 화면 목록은 바꾸지 않는다. 그것이 바뀌어야 하면 전체 재생성을 안내한다.
- **의존:** 23번의 묶음 프롬프트를 재사용한다. 23번 이후라면 S다.
- **테스트:** 대상 외 문서가 그대로인지, 리비전이 늘고 이전 리비전과 비교할 수 있는지.

### 18. 작업실 실시간 로그

- **현재:** 러너가 `process.communicate()`로 종료 후 출력을 한 번에 읽는다. 작업실은 3초마다 상태만 폴링한다.
- **설계:**
  1. 러너 출력을 줄 단위로 읽는 스레드가 시도별 로그 파일(`attempts/<id>/live.log`)에 덧붙인다. 비밀값은 기존 `redact`로 가린다. 파일 상한은 2MB이고, 넘으면 앞부분을 버리고 표시한다.
  2. 진행 이벤트를 받으려면 러너를 스트리밍 출력 모드로 바꿔야 한다. Claude는 `--output-format stream-json --verbose`, Codex는 `exec --json`, Gemini는 지원 여부를 확인해야 한다. 최종 결과 파싱은 지금과 같게 유지하고, 스트림에서 마지막 결과만 꺼낸다.
  3. 화면: 작업실 상세에 "실시간 로그" 패널을 둔다. `GET /api/agent/log?attempt=<id>&offset=<n>`이 새로 추가된 부분과 다음 offset을 돌려 준다. 실행 중에는 1초 간격으로 폴링하고 끝나면 멈춘다. SSE 대신 폴링을 쓰는 이유는 연결마다 서버 스레드를 오래 붙잡지 않고, 앱 종료·재시작 때 끊긴 연결을 따로 정리할 필요가 없으며, 같은 offset 방식을 CLI(`devroster task log --follow`)에도 쓰기 위해서다.
- **표시 수준:** 도구 호출("파일 읽음: src/a.py", "수정: src/b.py")과 모델 메시지 요약만 보인다. 모델의 내부 추론 내용은 저장하지 않는다(현재 실행 보기와 같은 원칙).
- **바꿀 곳:** `runners/*_cli.py`(스트림 읽기), `adapters/execution_view.py`(로그 API), `agent.js`(패널), 문서.
- **테스트:** 가짜 CLI가 천천히 출력할 때 offset 증가와 비밀값 가림, 상한을 넘을 때의 동작.
- **결정 필요:** 로그 보관 기간(권장: 작업 완료 후 30일, 백업 제외).

### 27. 완료된 작업의 워크트리 정리

- **현재:** `WorktreeManager.release()`는 작업 **취소** 때만 불린다. 그마저 기준 브랜치에 없는 커밋이 있으면 남긴다(`kept: commits not in the base`). GitHub에서 squash 병합하면 커밋 해시가 달라 영원히 "병합 안 됨"으로 보인다.
- **설계:** `devroster worktree list` / `devroster worktree prune`과 설정 화면의 "작업 폴더 정리" 카드를 둔다.
  - **정리 대상:** 완료되었거나 취소된 작업의 워크트리 중 다음 중 하나에 해당하는 것.
    - 작업 브랜치가 기준 브랜치에 포함됨
    - `publish_records.merge_state = 'merged'`(GitHub 병합 확인됨)
    - 로컬 완료로 기준 브랜치에 병합됨
  - **보존:** 커밋하지 않은 변경이 있거나 위 조건을 만족하지 않으면 남기고 이유를 보인다. (`--force`는 1차 구현에서 뺐다. 남은 폴더는 사용자가 확인하고 직접 정리한다.)
  - 미리보기(무엇을 지우고 얼마나 확보되는지) 후 확인 대화상자로 실행한다.
  - 작업을 완료할 때 "작업 폴더도 정리" 옵션을 둔다(기본 켬, 조건을 만족할 때만).
- **바꿀 곳:** `adapters/worktrees.py`(조건 판단), `command_line.py`, 설정 화면, `operations.md`.
- **테스트:** squash 병합 상황(브랜치 커밋이 기준에 없지만 `merge_state = 'merged'`), 변경 남음, `--force` 패치 저장.

### 12. Slack Socket Mode

- **현재:** `conversations.history`를 `poll_seconds`마다 조회한다. 공인 IP가 필요 없지만 지연과 호출 한도(Tier 3) 부담이 있다.
- **설계:**
  - 앱 수준 토큰(`xapp-`, `connections:write`)을 추가로 받는다. 연결 화면에 Socket Mode 켜기를 둔다(기본 꺼짐).
  - `apps.connections.open`으로 받은 `wss://` 주소에 표준 라이브러리(`ssl`, `socket`, `base64`, `hashlib`)로 최소한의 WebSocket 클라이언트(RFC 6455, 텍스트 프레임, ping/pong, close)를 구현한다. 예상 200줄 안팎이고 외부 의존성은 없다.
  - 이벤트(`message` in channel)를 받으면 envelope를 바로 `ack`하고, 기존 `handle()` 경로로 처리한다. 중복 방지는 기존 `processed`(ts)를 그대로 쓴다.
  - 연결이 끊기면 지수 백오프로 재연결하고, 연결이 안 되는 동안은 폴링으로 자동 전환한다.
- **보안:** 앱 토큰은 기존 비밀 저장소에 두고, 로그·화면에서 가린다. 수신 메시지는 지금처럼 허용된 채널과 사용자만 처리한다.
- **테스트:** 가짜 WebSocket 서버(로컬 소켓)로 handshake, 마스킹, ping/pong, 끊김 후 폴링 전환을 확인한다.
- **결정 필요:** Slack 앱 설정(Socket Mode 켜기, 이벤트 구독)을 사용자가 해야 하므로 설정 안내 문서가 필요하다.

### 20. 결과 JSON이 깨질 때

- **현재:** `parse_harness`는 코드 블록 안의 JSON이 정확히 하나여야 한다. 형식 오류나 블록 누락이면 바로 `INVALID_INPUT`으로 작업을 차단한다. 작은 모델일수록 잦다.
- **설계:**
  1. **엄격함 유지:** 중복 필드, 모르는 필드, 길이 초과, 잘못된 상태 값은 지금처럼 거부한다.
  2. **형식만 복구 요청:** 블록이 없거나 JSON 문법 오류일 때만, 같은 세션을 이어서(`resume`) 짧은 요청을 한 번 보낸다. "직전 답의 결과 블록이 형식에 맞지 않습니다. 파일을 고치지 말고 결과 JSON 블록만 다시 보내세요."
     - 이 요청에서 파일 변경이 생기면 거부한다(전후 캡처 비교).
     - 시도 횟수와 시간 한도에 포함하고, 이벤트 `ControlRepairRequested`를 남긴다.
  3. **관대한 위치 인식:** 코드 펜스 없이 출력 끝에 JSON 객체 하나만 있는 경우도 블록으로 인정한다. 그 밖의 텍스트 속 JSON은 인정하지 않는다.
  4. 세션 재개를 못 하는 러너(API 도구 일부)는 같은 입력으로 한 번 다시 실행하지 않고 바로 차단한다. 비용 때문이다.
  5. 세션으로 묶인 노드의 결과(공유 호출)는 복구 대상이 아니다. 단계식·워크플로 그래프 실행 모두 적용했다.
- **바꿀 곳:** `adapters/harness.py`, `application/workflow_dag.py`(역할 실행 후 복구 1회), `cli_runner.py`(재개 프롬프트).
- **테스트:** 펜스 누락, 쉼표 오류, 복구 요청 중 파일 변경, 복구 후에도 실패.

### 21. 프롬프트 길이

- **현재:** 역할 프롬프트(`artifacts.context`)에 승인된 설계 전문, 작업 정의, 저장소 바인딩, 이전 단계 근거(항목당 6,000자, 개수 제한 없음), 위키(역할 6,000자, 세션 24,000자), 스킬(노드당 4,000자), 프로젝트 룰, 지적 사항이 들어간다. 위키·스킬만 상한이 있고 **전체 크기를 측정하거나 보여 주는 곳이 없다**.
- **설계:**
  1. **측정 먼저:** 시도마다 프롬프트 항목별 글자 수를 `RunnerUsage` 이벤트에 `context_chars`로 남기고, 실행 보기에서 "프롬프트 구성"을 보인다. 측정 없이 줄이면 무엇을 잃는지 모른다.
  2. **예산:** 프로필 `context_policy.token_mode`(off / balanced / aggressive)에 항목별 상한을 붙인다. balanced 예시: 설계 20,000자, 이전 근거 합계 24,000자(최근 것부터), 지적 사항 20개. 넘치면 잘라 낸 사실과 원문 위치(산출물 경로)를 프롬프트에 적는다. 모델이 필요하면 파일로 읽을 수 있다.
  3. **역할 범위 줄이기:** 작업에 연결된 요구사항만 설계에서 추려 넣는다(Studio 인계 작업은 `requirement_ids`가 있다).
  4. 잘린 항목은 실행 보기의 경고에 보인다.
- **바꿀 곳:** `adapters/artifacts.py`(예산 적용), `domain/context_policy.py`(상한 정의), `execution_view.py`.
- **테스트:** 상한 초과 시 최신 근거가 남는지, 잘림 표시, 측정값 기록.
- **결정 필요:** 기본 모드(권장: balanced, 1차는 측정만 하고 자르기는 aggressive에서만).

### 28. 키체인 저장

- **현재:** `credential_store.py`가 API 키·토큰을 `credentials/shared/*.json`에 0600 권한으로 저장한다(Windows는 사용자 프로필 ACL).
- **설계:** 저장 방식 옵션 "운영체제 비밀 저장소"를 둔다(기본: 파일).
  - **macOS:** `security add-generic-password` / `find-generic-password` CLI. 서비스 이름 `DevRoster`, 계정은 `<connection_id>/<key>`.
  - **Windows:** `ctypes`로 `CredWriteW`·`CredReadW`·`CredDeleteW`(Generic credential).
  - **Linux:** `secret-tool`이 있으면 사용하고, 없으면 옵션을 끈다.
  - 파일에는 값 대신 `{"backend": "os", "ref": "..."}`만 남긴다. 전환(파일 → OS, OS → 파일) 명령을 두고, 백업은 비밀값을 지금처럼 제외한다.
  - CLI에 값을 넘길 때는 프로세스 목록에 보이지 않게 표준 입력을 쓴다(`security -w`는 인자로 받으므로 대화형 모드나 `-X` 대체를 시험해야 한다).
- **규모:** M. 플랫폼별 수동 확인이 필요하다.

### 29. 내장 코드 인덱서
